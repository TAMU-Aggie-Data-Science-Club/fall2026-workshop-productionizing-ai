# From an answer to a dependable service

> Archived material. Follow the [workshop README](../../README.md) for the current activity.

Imagine students asking a study assistant questions before an exam. One gets a
useful answer immediately. Another waits ten seconds. A third gets a quick but
incorrect explanation. Operating the service means understanding all three
experiences and deciding what to improve without hiding another problem.

## Follow one question

A **model** generates text from input. An **application** supplies that input,
calls the model, and handles everything around the call. Nimbus runs as a
**service**: a program that receives requests over the network. A **cache**
stores previous work for reuse; a cache hit means a matching entry was found.

For a question that needs a new answer, Nimbus follows this path:

1. **Check capacity.** Admit the request, make it wait for a slot, or reject it
   if the configured queue limit is reached.
2. **Look for a similar cached answer**, if semantic caching is enabled. A
   suitable match can skip retrieval and generation.
3. **Retrieve notes.** Search stored course-note chunks, which are short passages.
   An embedding represents text as numbers so the service can compare similarity.
4. **Assemble a prompt.** Combine instructions, selected notes, and the question.
   An exact answer-cache match at this point can skip generation.
5. **Select a model tier and generate.** Stream text back as it becomes available.
6. **Record the outcome and timings.** The client checks that the answer is
   nonempty and the stream completes.

Supplying retrieved information to a model is called **retrieval-augmented
generation (RAG)**. Relevant notes can help ground an answer, but their presence
does not prove that the answer uses them correctly. Read the answer and compare
it with the source.

## Read the measurements

| Term | Meaning in this workshop |
| --- | --- |
| Latency | Time from sending a request to completing its response |
| p95 latency | A value near the slow end of the measured successful requests: the 95th percentile |
| Time to first token (TTFT) | Time until the client sees the first answer text; it can differ greatly from completion time |
| Queue wait | Time waiting for a slot inside the application |
| Retrieval time | Time spent finding course-note passages |
| Generation time | Time in the model generation stage; it can include provider waiting and retries |
| Token | A unit of text used by a model; it may be a word, part of a word, or punctuation |
| Input / output tokens | Units supplied to / generated by the model; provider usage may also count reasoning tokens that are not displayed |
| Concurrency | Number of requests in progress at once; a client limit and a service admission limit control different parts of the path |
| Successful-request rate | Fraction of attempted requests that returned a complete, nonempty answer |
| Benchmark | A repeatable set of requests used to measure the service |
| Baseline | Your measurement before making a change; it may show an unhealthy service |
| Evaluation | Checks of answers against expected results |
| Trace | A record of the stages one request passed through, rather than the model's private reasoning |

A model token measures text. Your team token is a credential; these are different
uses of the word.

Read request outcomes first: fast results for a few successful requests can
hide many failures. Next, read the report's `p95 req` column. It breaks down
**one** request selected near the 95th percentile, so its rows add up to that
request's latency. The `p95 each` column computes a percentile for each stage
independently; those rows can come from different requests and do not add up.

For illustration, one request might spend 0.4 seconds in the application queue,
0.2 retrieving, 1.3 generating, and 0.1 in all remaining work: 2.0 seconds total.
Generation is the largest component, but that alone does not prove the model
tier is the cause. Input size, output length, or upstream retries could explain
it. These numbers illustrate arithmetic; they are not workshop targets.

The `client + network` row is the time left outside the measured server stages.
It can include platform waiting, startup, transit, and client work. It cannot
identify those causes separately. With a small run, such as 16 requests, the
p95 is sensitive to individual slow requests. Repeat the same workload when a
result is close to a target.

## Judge the whole result

Nimbus checks four aspects of recovery: response time, projected cost,
successful requests, and answer quality. It also checks that the observed
configuration stayed consistent during measurement and evaluation.

The cost report projects measured token use onto the exercise's monthly traffic
and adds an infrastructure allowance. It is not a bill and does not fully count
unsuccessful provider calls. Missing usage means cost is unknown.

The quality evaluator asks 36 questions: 24 fact-finding questions and 12
application or reasoning questions. It checks for expected keywords. A wrong
answer can contain a keyword, and a correct paraphrase can miss one. Inspect
actual answers as well, including a question requiring an explanation and one
the notes do not cover. A score is evidence about those checks, not a guarantee
of correctness for every user.

## Extend the lesson to agents

For this workshop, an **agent** is a system in which a model can choose a next
action, use a tool, inspect the result, and continue until a stopping condition.
A **tool** is an operation the application exposes, such as searching notes or
creating a calendar event. Nimbus uses a fixed retrieval-and-generation path;
it does not currently let the model choose and execute a sequence of tools.

Consider extending Nimbus to plan study sessions and add them to a calendar.
The same latency, cost, tracing, and evaluation practices still apply, but the
system now changes something outside the conversation. Use these design questions:

| Production concern | Design question for a calendar agent |
| --- | --- |
| Permissions | Which calendars may it read or change, and how is access checked outside the model? |
| Valid actions | Are tool arguments checked for valid dates, recipients, and allowed operations? |
| User control | Does the user review the proposed events before they are created? |
| Bounded work | What limits the number of steps, elapsed time, retries, and spending? |
| Safe retries | If a request times out after an event was created, how do you avoid creating it twice? |
| State | What progress must survive a process restart, and how will an interrupted task resume? |
| Untrusted content | How do you prevent instructions found in notes or tool output from granting new permissions? |
| Evaluation | Can tests check the final calendar state, denied actions, and partial failures as well as the answer text? |
| Monitoring and rollout | How will you detect problems, release to a small group, and restore the previous version? |

These are requirements to design and test in an extension, not capabilities
implemented by this exercise. Nimbus's public chat endpoint and in-memory
settings are workshop choices. A broader deployment needs decisions about user
authentication, data retention, abuse limits, durable state, and ongoing support.
